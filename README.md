# waferQC

저해상도(8×8, 64칸) 웨이퍼 결함 스크리닝 플랫폼 프로토타입 — **공정 엔지니어용 원인 추적 UI**.

분류 결과를 라벨로 끝내지 않고 "그래서 어느 공정부터 열어봐야 하나"까지 연결하는 것이 이
프로젝트에서 UI가 맡은 몫이다. 분류기를 의사결정 지원 도구로 확장하는 지점이 여기다.

> **개념 검증 프로토타입이다.** 실제 fab 데이터로 검증된 적 없고 상용 장비와 비교한 적도 없다.
> 화면 곳곳에 이 범위를 명시해 두었고, 그 문구를 지우지 말 것.

## 실행

`UI/start.bat`을 더블클릭하면 모델 서버와 화면이 각각 창 하나씩 뜨고 브라우저까지 열린다.
`node_modules`가 없으면 알아서 `npm install`부터 한다.

> `UI/start.bat`은 **CP949 + CRLF**로 저장해야 한다. UTF-8이나 LF로 저장하면 한글이 깨지고
> `if` 블록 파싱이 깨져서 창이 하나만 뜬다.

직접 띄우려면 창 두 개가 필요하다 (cmd 기준):

```
cd /d F:\waferQC\UI\backend\wafer_final_package_v2 && .venv\Scripts\python.exe serve.py
```

```
cd /d F:\waferQC\UI\frontend && npm run dev
```

http://127.0.0.1:5180 — `검사` 탭에서 패턴을 그리고 `판정하기`.

화면은 시작할 때 모델 서버(`:8077`)에 자동으로 붙는다. 서버가 없으면 규칙 대체판으로
떨어지면서 띄우는 법을 화면에 안내한다. 서버를 나중에 띄웠으면 새로고침할 것.

| 명령 | 하는 일 |
| --- | --- |
| `npm run dev` | 개발 서버 |
| `npm run build` | 프로덕션 빌드 |
| `npm run typecheck` | 타입 검사 |
| `npm run verify` | 프리셋 회귀 검사 — 판정 규칙을 고쳤을 때 반드시 돌릴 것 |
| `npm run verify:model` | **실제 모델 서버와 대조** — README 예시 8종이 CLI와 같은 판정을 내는지 |

## 화면

| 탭 | 내용 |
| --- | --- |
| **검사** | 판정 엔진 연결 → 8×8 패턴 입력 → 판정 → **공정별 원인 추적** → 점검 보고서 |
| **이력** | 대응 Log 315건 + 과거 검사 기록, 점검 진행 상황, 조치 결론 기록 |

화면은 **엑셀 두 개와 모델 패키지가 근거를 대는 것만** 남겼다. 하드웨어 스캔 모사, 열람 권한·감사
로그, 사내 매뉴얼 참조, 공정별 계측지표 표는 근거가 없어 걷어냈다.

## 두 층으로 된 판정

모델은 **9클래스**(Center / Donut / Edge-Loc / Edge-Ring / Loc / Random / Scratch / Near-full / None)를
출력한다. UI는 그걸 그대로 띄우지 않고 두 층으로 보여준다.

1. **계통** — 9클래스를 6개 계통(정상 / 중심계 / 외곽계 / 국부계 / 산발계 / 전면계)으로 묶은 확률.
   8×8에서는 인접 클래스끼리 확률이 새기 때문에 계통 단위가 훨씬 안정적이다.
2. **9클래스 확률** — 모델 원본. 각 후보에 **어느 피처가 그 순위를 만들었는지** 실제 수치를 인용한 근거를 붙인다.

각 클래스는 정확히 한 계통에만 속하므로 계통 확률은 소속 클래스 확률의 합이고, 합이 보존된다.

### 못 하는 것을 못 한다고 말한다

8×8에서 구조적으로 갈리지 않는 쌍(Center↔Donut, Donut↔Edge-Ring, Loc↔Scratch, Edge-Loc↔Edge-Ring)은
판정 화면의 **"이 판정의 한계"**에 근거와 함께 그대로 노출된다. 대신 그 둘을 가르는 데 쓰이는
연속 수치(군집 이방성, 외곽 각도 분산)를 판정 근거로 같이 내보내 엔지니어가 직접 읽게 한다.

### 사람 검토 여부를 판정보다 먼저

"이 판정을 그대로 믿고 공정을 열어도 되는가"가 클래스 이름보다 먼저 답해야 할 질문이다.
모델의 검토 정책(1순위 확률 부족 / 항상 검토 클래스 / 불량 밀도 극단 등)에 걸리면
판정 카드 **위에** 사유와 함께 경고가 뜬다.

## 데이터 원본은 엑셀이다

원인 지식베이스는 코드가 아니라 **팀이 관리하는 엑셀 두 개**가 원본이다.

팀원이 관리하는 원본이라 `data/` 아래에 따로 두고, 코드에서는 읽기만 한다.

| 파일 | 담는 것 |
| --- | --- |
| `data/반도체 불량 분석 개선안.xlsx` | 공정(6) × 결함유형(8) × 불량 유형(①②) → **원인 / 해결 / 개선** |
| `data/불량 대응 log.xlsx` | 2025-08 ~ 2026-08 대응 이력 315건 (92종 × 2~5회 재발) |

`UI/frontend/scripts/gen_from_xlsx.py`가 이 둘을 읽어 아래 두 파일을 생성한다.

```bash
cd UI/frontend && python scripts/gen_from_xlsx.py
```

- `UI/frontend/src/domain/causeMatrix.generated.ts` — 원인 69건 + 유발근거 서술 4건
- `UI/frontend/src/services/historySeed.generated.ts` — 대응 이력 315건

> **엑셀은 절대 코드에서 수정하지 않는다.** 내용이 틀렸으면 엑셀을 고치고 스크립트를 다시 돌린다.
> 생성된 `*.generated.ts`도 직접 손대지 말 것 — 다음 생성 때 덮어써진다.

엑셀의 세 칸이 이 화면의 골격이다. **해결**은 오늘 당직이 이 로트에 하는 일이고, **개선**은 공정
담당이 계획을 잡는 일이라 화면에서도 섞지 않는다.

## 원인 추적이 실제로 하는 일

`src/domain/plan.ts`가 매트릭스를 이번 측정에 맞춰 공정별로 재배열한다. 순위는 네 가지를 같이 본다.

1. 세부 패턴 후보의 확률 — 유력한 패턴의 원인 공정일수록 위로
2. 엑셀의 불량 유형 ①/② — ①이 그 공정의 대표 원인
3. **대응 Log의 재발 빈도** — 지난 12개월 실제로 자주 터진 원인일수록 위로
4. **이번 측정의 방위가 그 원인의 방향성 서명과 맞는가**

3·4번이 이 UI가 조회표 이상인 지점이다. 예를 들어 *"Slit Valve 개폐 시 유입 파티클"*은 로그에
**9시 방향**으로 기록돼 있어서, 측정된 결함 방위가 실제로 9시면 **"✔ 이번 측정이 지지 — 사실상
확정에 가깝다"**로 1순위에 올라오고, 3시면 **"△ 측정과 불일치"**로 내려간다. 같은 패턴이라도
측정과 이력에 따라 순서가 바뀐다.

또 하나의 구분: 방향성이 있어도 **각도가 설비 배치에 달려 있어 웨이퍼 한 장으로는 못 가리는 원인**이
있다 (Lift Pin, RF Feedthrough, Retainer Ring Joint, WEE 스캔 기준점 등 6건). 로그가 이들을
`장비 구조 의존`으로만 적고 숫자를 안 박아 둔 걸 그대로 따라, `⚙ 설비 배치 실측 필요`로 갈라 둔다.
근거 없는 각도를 확정처럼 띄우면 엔지니어를 엉뚱한 방위로 보낸다.

**"유발하지 않는다"와 "빈칸"도 구분한다.** 엑셀에는 *"Scanner 노광은 Reticle Field 단위라 도넛형
불량을 유발할 가능성 매우 낮음"* 같은 근거가 4칸 적혀 있는데, 이건 지식베이스의 공백이 아니라
판단이므로 공정 탭 하단에 근거째로 보여준다. 반대로 아직 안 채워진 공정·패턴은 그대로 드러낸다 —
안 보이는 것과 "배제되었다"는 건 다르다.

## 8×8 격자

모델 패키지의 입력 형상이 8×8(64칸)이다. 원형 웨이퍼를 정사각 8×8 격자에 얹으면 네 모서리
12칸이 웨이퍼 밖이라 **유효 셀은 52칸**이다. 그 12칸은 모델 입력에서 `0`(웨이퍼 밖)이고,
불량 비율 계산의 분모에서도 빠진다.

## 구조

앱은 `UI/` 아래에 프론트·백을 함께 두고, **팀에서 받은 것은 밖으로 뺐다.**
`data/`의 엑셀 원본과 `UI/backend/wafer_final_package_v2/`의 모델 패키지가 그것이고,
내용은 물론 **파일·폴더 이름도 받은 그대로** 둔다 — 위치만 옮겼다.

```
data/                    ★ 팀원 제공 원본 (읽기 전용)
  반도체 불량 분석 개선안.xlsx
  불량 대응 log.xlsx
docs/                    연동 절차 · 모델 계약
UI/
  backend/
    wafer_final_package_v2/ ★ 팀 제공 모델 패키지 — serve.py · models/ · .venv (git 제외)
  frontend/              ↓ 이 저장소가 만드는 것
src/
  config/
    hardware.ts    8×8 격자 상수 · 원형 마스크 판정
    model.ts       ★ 모델 계약 — 9클래스 순서, 셀 값, 검토 정책
    taxonomy.ts    계통 체계, 미분리 쌍과 그 근거
  domain/
    types.ts       공용 타입
    features.ts    8×8 → 공간 통계 (반경·군집·이방성·방위)
    classify.ts    규칙 기반 대체 분류기 (모델 미연결 시 · 이력 시드 생성에도 쓰인다)
    review.ts      사람 검토 필요 여부 판정
    causes.ts      ★ 공정 × 결함유형 → 원인·해결·개선 (타입·헬퍼)
    causeMatrix.generated.ts   ⚙ 엑셀에서 생성 — 직접 수정 금지
    caseStatus.ts  대응 Log '상태' 열 → 화면·보고서 공통 문구
    plan.ts        ★ 판정 → 공정별 점검 계획
    patterns.ts    프리셋 패턴 + 모델 README 예시 입력
  services/        ★ 실제 연결 교체 지점
    inference.ts   모델 추론 (규칙 / HTTP 어댑터)
    history.ts     검사 이력 (localStorage → MES·DB)
    historySeed.generated.ts   ⚙ 대응 Log 315건 — 직접 수정 금지
    report.ts      점검 보고서 생성 (마크다운)
    reportImage.ts 점검 보고서 PNG 렌더
  components/  pages/  styles/
scripts/
  gen_from_xlsx.py   ⚙ data/ 엑셀 → 위 두 generated 파일
  verify-presets.ts  프리셋 회귀 검사
  verify-model-server.ts  실제 모델 서버 대조
```

자세한 연동 절차는 [docs/INTEGRATION.md](docs/INTEGRATION.md),
모델과 맞춰야 하는 계약은 [docs/MODEL_CONTRACT.md](docs/MODEL_CONTRACT.md).

## 판정 규칙을 고칠 때

`npm run verify`가 프리셋 9종의 계통·1순위 클래스를 회귀 기준선과 대조한다.
기준선이 깨지면 **고친 게 맞는지 기준선이 틀렸는지를 먼저 판단하고** 둘 중 하나를 고칠 것.

이 하네스가 실제로 잡아낸 것들:

- 대각 스크래치가 4-연결로 5개 군집으로 쪼개지던 문제 → 8-연결로 교체
- 8×8에서 외곽 링만으로 밀도 임계를 넘어 Edge-Ring이 Near-full로 오분류되던 문제
  → 전면의 서명은 밀도가 아니라 "최내측까지 찼는가"
- **링의 평균 반경은 정의상 중간값**이라 무게중심으로는 Donut을 절대 못 잡던 문제
  → 반경 프로파일의 형상(한 구간이 꽉 참 + 최내측 빔 + 중심을 둘러쌈)으로 판별
- 외곽 링에 붙은 군집이 격자 기하 때문에 저절로 직선이 되어 전부 Scratch로 읽히던 문제
