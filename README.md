# waferQC

저해상도(8×8, 64칸) 웨이퍼 결함 스크리닝 플랫폼 프로토타입 — **공정 엔지니어용 원인 추적 UI**.

분류 결과를 라벨로 끝내지 않고 "그래서 어느 공정부터 열어봐야 하나"까지 연결하는 것이 이
프로젝트에서 UI가 맡은 몫이다. 분류기를 의사결정 지원 도구로 확장하는 지점이 여기다.

> **개념 검증 프로토타입이다.** 실제 fab 데이터로 검증된 적 없고 상용 장비와 비교한 적도 없다.
> 이 범위는 점검 보고서 꼬리말(마크다운·PNG 둘 다)에 적혀 있다 — *"확정 진단이 아니라 점검
> 우선순위를 좁히기 위한 것"*. 보고서는 화면 밖으로 나가는 산출물이라 그 문구를 지우지 말 것.
> 화면에서는 헤드바의 `실제 모델` / `규칙 대체판` 배지가 지금 무엇으로 판정 중인지를 말한다.

**이 파일 하나가 저장소의 유일한 문서다.** 실행법·하드웨어 배선·모델 계약·연동 절차가 전부
여기 있다. 같은 수치가 두 군데 적혀 있으면 반드시 한쪽이 낡으므로, 값은 이 문서와 코드에만 둔다.

## 실행

`UI/start.bat`을 더블클릭하면 모델 서버 · 화면 · 아두이노 브리지가 각각 창 하나씩 뜨고
브라우저까지 열린다. `node_modules`가 없으면 알아서 `npm install`부터 한다.

> `UI/start.bat`은 **CP949 + CRLF**로 저장해야 한다. UTF-8이나 LF로 저장하면 한글이 깨지고
> `if` 블록 파싱이 깨져서 창이 하나만 뜬다.

직접 띄우려면 창 세 개가 필요하다 (cmd 기준):

```
cd /d F:\waferQC\UI\backend\wafer_final_package_v2 && .venv\Scripts\python.exe serve.py
```

```
cd /d F:\waferQC\UI\frontend && npm run dev
```

```
cd /d F:\waferQC\UI\backend && wafer_final_package_v2\.venv\Scripts\python.exe serial_bridge.py
```

| 프로세스 | 포트 |
| --- | --- |
| 판정 모델 서버 `serve.py` | 8077 |
| 화면 (Vite) | 5180 |
| 아두이노 시리얼 브리지 `serial_bridge.py` | 8078 |

브리지 없이도 화면은 뜨고, `패턴 선택` 카드의 `하드웨어 없이 이 패턴으로 판정`으로
판정까지 된다 — 다만 되읽기 검증이 빠진 판정이고 이력에 `draw`로 남는다. 보드를 붙이면
같은 자리의 버튼이 `이 패턴으로 판정하기`로 바뀌고, 판정 입력은 되읽은 맵이 된다.

http://127.0.0.1:5180 — `검사` 탭. 패턴을 그리면(기본값 `칸을 찍을 때마다 자동 송출`)
쓰기 아두이노로 나가고, 같은 카드 아래 `이 패턴으로 판정하기`를 누르면 읽기 아두이노가
되읽은 맵으로 판정한다.

화면은 시작할 때 모델 서버(`:8077`)와 브리지(`:8078`)에 자동으로 붙는다. 모델 서버가 없으면
규칙 대체판으로 떨어지면서 띄우는 법을 화면에 안내한다 — 나중에 띄웠으면 새로고침할 것.
브리지는 나중에 띄워도 새로고침 없이 카드의 `재연결`로 붙는다.

터널로 남에게 보여줄 때는 두 주소가 개발 서버 프록시 `/model` · `/hw`로 자동으로 바뀐다.
원격 브라우저의 127.0.0.1에는 모델 서버도 브리지도 없기 때문이다 — `vite.config.ts` 참고.

## 하드웨어 — 아두이노 2대

`검사` 탭의 `하드웨어 연결` 카드가 실물 보드를 붙인다. 펌웨어는 `code/` 폴더가 정본이고
UI 쪽이 거기에 맞춘다.

```
화면에 찍은 불량 ──▶ 쓰기(출력) 아두이노 ──▶ 74HC595 래치
                                                    │  (실물 보드)
                        읽기(입력) 아두이노 ◀───────┘  CD4067 스캔
                                ├──▶ NeoPixel 8x8 : 읽어낸 값을 눈으로
                                ▼
                             판정 입력
```

| 역할 | 펌웨어 | 배선 | 하는 일 |
| --- | --- | --- | --- |
| 출력(쓰기) | `code/쓰기아두이노/prototype_arduino/prototype_arduino.ino` | 5V, GND, D2 D3 D4 | 화면 패턴을 74HC595 체인에 래치. **그게 전부다.** |
| 입력(읽기) | `code/read_arduino/read_arduino.ino` | D5~D8, A0~A3, D9, GND | CD4067 4개로 스캔 → 시리얼로 올림 + **NeoPixel 8x8 표시** |

LED 매트릭스는 **읽기 보드**에 달려 있다(D9). 그래서 매트릭스에 뜨는 건 보내온 값이 아니라
이 보드가 **실제로 읽어낸** 값이다. 매트릭스도 읽기 쪽에만 있으므로 정보 격벽은 그대로다.

두 대 사이에는 전선만 있고 통신이 없다. 읽기 쪽은 4067의 COMMON을 읽기만 하므로
읽기 → 쓰기 방향으로 정보가 흐를 길 자체가 없다 — `read_arduino.ino`가 말하는 정보 격벽이다.

**보드가 붙어 있으면 판정 입력은 되읽은 맵 하나뿐이다.** 화면에 그린 패턴은 쓰기
아두이노로 내보내는 출력이고, 판정에는 들어가지 않는다 — 되읽는 과정에서 비트가 새면
판정도 같이 달라져야 하고, 그게 이 경로를 거치는 이유다. 화면 맵으로 **조용히 대체되는
경로는 없다**: 보드가 없을 때만 버튼이 `하드웨어 없이 이 패턴으로 판정`으로 바뀌고,
그렇게 나온 판정은 이력에 `draw`로 기록된다 (`AppStore.runInspection`).

**되읽은 맵은 화면에 격자로 그리지 않는다.** 읽기 보드의 LED 매트릭스가 같은 값을 실물로
띄우고 있어서 화면 격자는 그걸 복제할 뿐이었다. `하드웨어 연결` 카드는 연결과 송출만 맡는다 —
포트 배지, 연결 실패 안내, `칸을 찍을 때마다 자동 송출` · `지금 보내기` · `재연결`.

> **보낸 맵과 되읽은 맵이 어긋나도 에러는 안 난다.** `패턴 선택` 카드의 판정 버튼 바로 아래
> 뜨는 "어긋난 칸 수"가 유일한 신호다. 0이 아니면 배선이나 극성부터 볼 것 — 전부 어긋나면
> 읽기 쪽 HIGH/LOW 반전이다.

### 시리얼 프로토콜

9600 baud, 개행 종단. `serial_bridge.py`가 이 문자열을 전부 흡수하고, 프론트로는 0/1/2 맵만 올라간다.

```
호스트 -> 쓰기 아두이노   D:<64자리 0/1>    row-major, 1 = 불량
쓰기 아두이노 -> 호스트   OK                595 래치 완료 (되읽기가 아니다)
읽기 아두이노 -> 호스트   D:<64자리 0/1>    값이 바뀔 때마다 자발적으로
```

`OK`는 접수 확인일 뿐이다. 실제로 잘 걸렸는지는 읽기 아두이노가 올리는 맵으로만 알 수 있고,
그게 이 구조의 요점이다. 브리지는 이 응답으로 두 보드를 구분한다 — 읽기 보드는 가만히 둬도
`D:`를 올리고, 쓰기 보드는 받기 전엔 조용하다. (옛 펌웨어의 `R:`도 아직 받아준다.)

**값 변환** — 화면/모델 맵은 0(웨이퍼 밖)/1(정상)/2(불량) 세 값, 펌웨어는 0/1 두 값이다.
브리지가 되읽은 비트에 웨이퍼 마스크를 다시 씌운다.

⚠ **웨이퍼 밖 12칸의 정의가 세 곳에 있다** — `read_arduino.ino`의 `isOutsideWafer()`(LED 표시용),
`serial_bridge.py`의 `_inside()`, `config/hardware.ts`의 `isInsideWafer()`. 셋이 같아야 하고,
한 곳만 바뀌면 화면과 매트릭스의 모서리가 조용히 달라진다.

⚠ **매트릭스 방향**은 `read_arduino.ino`의 `mapIndexToLED()` 한 줄이 정한다. 현재 매트릭스가
180도 돌아가 달려 있어 `return 63 - i`다. 모서리 마스크는 180도 회전에 대칭이라 이 어긋남을
**드러내지 못하므로**, 방향 확인은 반드시 비대칭 패턴으로 할 것. 다른 배선(좌우/상하 반전,
지그재그, 행열 교환)의 식은 그 함수 주석에 적어 두었다.

### 브리지

```
cd /d F:\waferQC\UI\backend
wafer_final_package_v2\.venv\Scripts\python.exe serial_bridge.py
```

포트는 자동으로 갈린다 — 읽기 아두이노는 가만히 둬도 `D:`를 올리고, 쓰기 아두이노는 받기
전에는 조용하다. **COM 번호로 고르지 않는다.** 자동 판별이 틀리면
`--read-port COM11 --write-port COM12`로 직접 박고, 되읽은 맵이 통째로 불량으로 보이면
읽기 쪽 HIGH/LOW가 뒤집힌 것이니 `--invert-read`로 띄운다.

### 확인해야 할 것

- **되읽은 맵이 보낸 맵과 일치하는가.** 판정 버튼 아래 어긋난 칸 수가 항상 뜬다.
  맵이 뒤섞여도 **에러는 안 난다** — 이 수치가 유일한 신호다.
- **좌표 방향** — `row 0 = 위`, `col 0 = 왼쪽` 기준이다. 배선이 상하/좌우 반전돼 있으면 방향
  판정이 통째로 뒤집힌다. 한 모서리에만 불량을 넣는 비대칭 패턴으로 한 번 검증할 것.
- **쓰기 보드는 595만 건드린다.** 예전엔 NeoPixel 표시와 4067 되읽기 스캔이 같이 들어 있었으나
  그 보드엔 D9도 D5~D8/A0~A3도 꽂혀 있지 않아 뜬 핀을 읽고 있었다. 둘 다 걷어냈다
  (4040바이트, 12%). 4067 주소선을 두 보드가 동시에 구동할 위험도 같이 없어졌다.
- **포트를 다른 프로그램이 잡고 있으면 안 된다.** Arduino IDE의 시리얼 모니터가
  열려 있으면 브리지가 그 포트를 못 연다 (`PermissionError 13`). 모니터를 닫고
  화면의 `재연결` 버튼을 누른다.

## 두 층으로 된 판정

모델은 **9클래스**(Center / Donut / Edge-Loc / Edge-Ring / Loc / Random / Scratch / Near-full / None)를
출력한다. UI는 그걸 그대로 띄우지 않고 두 층으로 보여준다.

1. **계통** — 9클래스를 6개 계통(Normal / Radial · Center-weighted / Radial · Edge-weighted /
   Localized / Scattered / Global)으로 묶은 확률. 계통 이름은 모델의 9클래스와 섞이지 않게
   화면·보고서 모두 영문으로 통일했다 (`config/taxonomy.ts`).
   8×8에서는 인접 클래스끼리 확률이 새기 때문에 계통 단위가 훨씬 안정적이다.
2. **9클래스 확률** — 모델 원본. 각 후보에 **어느 피처가 그 순위를 만들었는지** 실제 수치를 인용한 근거를 붙인다.

각 클래스는 정확히 한 계통에만 속하므로 계통 확률은 소속 클래스 확률의 합이고, 합이 보존된다.

### 못 하는 것을 못 한다고 말한다

8×8에서 구조적으로 갈리지 않는 쌍(Center↔Donut, Donut↔Edge-Ring, Loc↔Scratch, Edge-Loc↔Edge-Ring)은
숨기지 않는다. 어느 쌍이 왜 안 갈리는지는 점검 보고서 §3 **"이 판정의 한계"**에 근거와 함께
적힌다 (`config/taxonomy.ts`의 `UNRESOLVED_PAIRS`). 화면에서는 검토 사유 **"구조적으로 모호한
클래스"**로 뜨는데, 지금은 검토 표시를 꺼 둬서(아래) 보고서 쪽에만 남는다. 대신 그 둘을
가르는 데 쓰이는 연속 수치(군집 이방성, 외곽 각도 분산)는 `판정 근거` 표에 항상 실려
엔지니어가 직접 읽는다.

### 검토 정책 — 지금은 화면에 표시하지 않는다

"이 판정을 그대로 믿고 공정을 열어도 되는가"는 클래스 이름보다 먼저 답해야 할 질문이지만,
**지금은 화면·보고서에 띄우지 않는다** (`config/model.ts`의 `SHOW_REVIEW_STATUS = false`).
클래스별 임계 6개가 자리표시자 `1.01`이라 거의 모든 판정에 "검토 필요"가 붙는데, 실측
임계가 들어오기 전까지 그 경고는 판정에 대해 아무것도 알려 주지 않으면서 화면만 덮는다.

**정책 자체는 그대로 돈다** — 서버는 `review_reason`을 계속 내려주고 `verdict.review`도
채워진다. 표시만 꺼져 있고, 실측 임계가 들어오면 `SHOW_REVIEW_STATUS`를 `true`로 되돌리면
된다. 그 한 줄로 판정 화면 · 보고서 마크다운 · 보고서 PNG가 같이 돌아온다.

켰을 때: 판정 카드 **위에** 사유 이름이 뜨고 `왜?`를 누르면 설명이 펼쳐진다. 실제 모델
서버에 붙어 있으면 사유는 서버가 내려주는 `review_reason`을 그대로 쓰고, 규칙 대체판일 때만
`domain/review.ts`가 같은 정책을 화면에서 돌린다. 정책값은 아래 「모델 계약」에 있다.

## 모델 계약

UI와 모델이 맞춰야 하는 것들. 출처는 `ConvNeXt_CNN.ipynb`가 내보내는
`final_hardware_inference_policy.json`이고, 코드에서는 **`src/config/model.ts` 하나**가 정본이다.

> 여기가 어긋나면 판정이 **조용히** 틀어진다. 에러도 안 나고 화면도 정상으로 보이는데
> 라벨만 밀려 있는 상태가 된다. 모델을 재학습하면 policy JSON을 받아 아래를 대조할 것.

### 입력

| 항목 | 값 |
| --- | --- |
| 형태 | `[8, 8]` 정수 배열 |
| 값 | `0` = 웨이퍼 밖 · `1` = 정상 die · `2` = 불량 die |
| 모델 전처리 | `F.one_hot(map, 3).permute(2,0,1).float()` → `(3, 8, 8)` |

원형 웨이퍼를 정사각 8×8 격자에 얹으면 네 모서리 12칸이 웨이퍼 밖이라 **유효 셀은 52칸**이다.
그 12칸은 모델 입력에서 `0`이고, 불량 비율 계산의 분모에서도 빠진다.

`config/model.ts`의 `CONVERSION_DEFECT_THRESHOLD`(0.05)와 `WAFER_PRESENCE_THRESHOLD`(0.25)는
**노트북이 고해상도 WM-811K 맵을 8×8로 줄일 때** 쓰는 값이다. 우리 하드웨어는 한 칸이 곧
센서 하나라 다운샘플링이 없고, 지금 읽기 보드는 4067로 디지털 0/1을 읽는다 — 아날로그 값을
가르는 임계는 UI에 없다. 실물 센서를 아날로그로 바꾸면 그 임계를 새로 잡아야 하고, 그렇게
만들어진 8×8 분포가 모델 학습 분포와 맞는지도 같이 확인해야 한다.

### 출력 — 9클래스

**순서가 곧 모델 출력 인덱스다.** 바꾸면 라벨이 전부 밀린다.

```
0 Center   1 Donut     2 Edge-Loc   3 Edge-Ring   4 Loc
5 Random   6 Scratch   7 Near-full  8 None
```

| 모델 | 역할 |
| --- | --- |
| `WaferCNNV2` (primary) | 9클래스 최종 예측 |
| `WaferHierarchicalCNNV3` (auxiliary) | 검토 판단 보조, 이진(정상/불량) 임계 보유. **화면에는 표시하지 않는다** — 판정은 주 모델 하나로 읽고, 두 모델이 갈린 사실은 검토 사유에만 남는다 |

### 계통 매핑

각 클래스는 **정확히 한 계통에만** 속한다 — 겹치면 계통 확률의 합이 1을 넘는다.

| 계통 | 클래스 |
| --- | --- |
| NORMAL — Normal | None |
| RADIAL_INNER — Radial · Center-weighted (`Inner`) | Center, Donut |
| RADIAL_OUTER — Radial · Edge-weighted (`Edge`) | Edge-Ring, Edge-Loc |
| LOCAL — Localized (`Local`) | Loc, Scratch |
| SCATTER — Scattered (`Scatter`) | Random |
| GLOBAL — Global (`Global`) | Near-full |

화면·보고서에 뜨는 이름이 이 영문 라벨이다. 괄호 안은 배지·목록에 쓰는 짧은 이름.

### 검토 정책 값

| 상수 | 값 | 뜻 |
| --- | --- | --- |
| `LOW_PRIMARY_SCORE` | 0.60 | 1순위 확률이 이 아래면 검토 |
| `ALWAYS_REVIEW_CLASSES` | `Random`, `Near-full` | 확률과 무관하게 항상 검토 |
| `HIGH_DEFECT_CELL_THRESHOLD` | 10 | 불량 칸이 이 개수 이상이고 판정이 `None`/`Random`이면 검토. 기준은 64칸이 아니라 웨이퍼 안 52칸이라 10칸 ≈ 19% |
| `NONE_REVIEW_THRESHOLD` | 0.49 | 정상 판정인데 불량 근거가 이만큼 있으면 검토 |
| `V3_BINARY_THRESHOLD` | 0.68 | 보조 모델 이진 임계 (서버 대조용 · 화면 미표시) |

`classwise_score_thresholds`는 지금 9개 중 6개(Center · Donut · Edge-Loc · Random · Scratch ·
Near-full)가 `1.01`이다. 확률이 넘을 수 없는 값이라 그 클래스는 늘 검토로 분류된다 —
모델 담당자가 실측값을 넣기 전까지의 자리표시자이고, 검토 표시를 꺼 둔 이유가 이것이다.

값은 모두 모델 패키지의 `config.json`이 정본이고 `config/model.ts`가 그걸 따라간다.
노트북이 내보내는 `review_reasons` 코드 11종은 `REVIEW_REASON_COPY`에 한국어 설명과 조치까지
같이 적어 두었다. 코드만 화면에 띄우면 엔지니어가 읽을 수 없다.

### HTTP 계약

```
POST {baseUrl}/predict
요청  { "hardware_map": number[8][8] }        // 0 / 1 / 2
```

응답 (`services/inference.ts`의 `PredictResponse`). **필드명은 `wafer_model.py`의
`WaferInferenceSystem.predict()` 반환값 그대로다** — `serve.py`는 감싸기만 하고 이름을 바꾸지 않는다.

```jsonc
{
  "prediction": "Edge-Loc",              // 최종 1순위 — UI 는 이걸 그대로 쓴다
  "score": 0.31,
  "status": "REVIEW",                    // ACCEPT | REVIEW
  "review_reason": ["low_primary_score"],// 배열. 이름이 단수형인 것에 주의
  "class_threshold": 1.01,
  "none_review_threshold": 0.49,
  "top_predictions": [{ "class": "Edge-Loc", "score": 0.31 }],
  "auxiliary_prediction": "Edge-Loc",    // V3. UI 는 표시하지 않는다
  "auxiliary_score": 0.74,
  "v3_defect_score": 0.88,
  "v3_binary_threshold": 0.68,
  "defect_cell_count": 8,
  "direction": "9시",                    // Scratch · Loc · Edge-Loc 에만
  "direction_confidence": 0.62,
  "direction_method": "max_vs_other_mean",
  "quadrant_counts": { "top_left": 5, "top_right": 1, "bottom_left": 2, "bottom_right": 0 },

  // serve.py 가 덧붙이는 것
  "probabilities": [0.02, 0.01, 0.31, 0.03, 0.30, 0.03, 0.25, 0.03, 0.02],
  "class_names": ["Center", "Donut", "..."],
  "model": "WaferCNNV2"
}
```

`probabilities`는 **9개 전부** 내려주는 게 좋다. `top_predictions`만 오면 나머지 클래스가 0으로
채워져 계통 합이 실제보다 낮게 나온다. CORS도 열어야 한다.

서버를 바꿔 끼우는 자리는 `services/inference.ts`의 `HttpInferenceEngine` 하나다.

```ts
setInferenceEngine(new HttpInferenceEngine('http://<서버>:<포트>'));
```

## 데이터 원본은 엑셀이다

원인 지식베이스는 코드가 아니라 **팀이 관리하는 엑셀 두 개**가 원본이다.

팀원이 관리하는 원본이라 `data/` 아래에 따로 두고, 코드에서는 읽기만 한다.

| 파일 | 담는 것 |
| --- | --- |
| `data/반도체 불량 분석 개선안.xlsx` | 공정(6) × 결함유형(8) × 불량 유형(①②) → **원인 / 해결 / 개선** |
| `data/불량 대응 log.xlsx` | 2025-08 ~ 2026-08 대응 이력 315건 (92종 × 2~5회 재발) |

`UI/frontend/scripts/gen_from_xlsx.py`가 이 둘을 읽어 아래 두 파일을 생성한다.

```bash
cd UI/frontend && python scripts/gen_from_xlsx.py
```

- `UI/frontend/src/domain/causeMatrix.generated.ts` — 원인 69건 + 유발근거 서술 4건
- `UI/frontend/src/services/historySeed.generated.ts` — 대응 이력 315건

> **엑셀은 절대 코드에서 수정하지 않는다.** 내용이 틀렸으면 엑셀을 고치고 스크립트를 다시 돌린다.
> 생성된 `*.generated.ts`도 직접 손대지 말 것 — 다음 생성 때 덮어써진다.

엑셀의 세 칸이 이 화면의 골격이다. **해결**은 오늘 당직이 이 로트에 하는 일이고, **개선**은 공정
담당이 계획을 잡는 일이라 화면에서도 섞지 않는다.

지식베이스가 비어 있을 때 지켜지는 것:

- **매핑이 없는 공정 × 패턴 조합은 화면에 그대로 드러낸다.** 안 보이는 것과 "배제되었다"는 건
  다르므로, 공정 탭에 `매핑된 원인이 없는 공정`으로 이름만 남긴다.
- **"유발하지 않는다"는 빈칸이 아니다.** 엑셀에 판단 근거가 적힌 칸 4개는 `EXCLUSION_NOTES`로
  들어가 공정 탭 하단에 근거째로 뜬다.

## 원인 추적이 실제로 하는 일

`src/domain/plan.ts`가 매트릭스를 이번 측정에 맞춰 공정별로 재배열한다. 순위는 네 가지를 같이 본다.

1. 세부 패턴 후보의 확률 — 유력한 패턴의 원인 공정일수록 위로
2. 엑셀의 불량 유형 ①/② — ①이 그 공정의 대표 원인
3. **대응 Log의 재발 빈도** — 지난 12개월 실제로 자주 터진 원인일수록 위로
4. **이번 측정의 방위가 그 원인의 방향성 서명과 맞는가**

3·4번이 이 UI가 조회표 이상인 지점이다. 예를 들어 *"Slit Valve 개폐 시 유입 파티클"*은 로그에
**9시 방향**으로 기록돼 있어서, 측정된 결함 방위가 실제로 9시면 **"✔ 이번 측정이 지지 — 사실상
확정에 가깝다"**로 1순위에 올라오고, 3시면 **"△ 측정과 불일치"**로 내려간다. 같은 패턴이라도
측정과 이력에 따라 순서가 바뀐다.

또 하나의 구분: 방향성이 있어도 **각도가 설비 배치에 달려 있어 웨이퍼 한 장으로는 못 가리는 원인**이
있다 (Lift Pin, RF Feedthrough, Retainer Ring Joint, WEE 스캔 기준점 등 6건). 로그가 이들을
`장비 구조 의존`으로만 적고 숫자를 안 박아 둔 걸 그대로 따라, `⚙ 설비 배치 실측 필요`로 갈라 둔다.
근거 없는 각도를 확정처럼 띄우면 엔지니어를 엉뚱한 방위로 보낸다. 실제 설비 배치 각도를 받으면
이들도 방위 대조 대상으로 올릴 수 있다.

**"유발하지 않는다"와 "빈칸"도 구분한다.** 엑셀에는 *"Scanner 노광은 Reticle Field 단위라 도넛형
불량을 유발할 가능성 매우 낮음"* 같은 근거가 4칸 적혀 있는데, 이건 지식베이스의 공백이 아니라
판단이므로 공정 탭 하단에 근거째로 보여준다. 반대로 아직 안 채워진 공정·패턴은 그대로 드러낸다 —
안 보이는 것과 "배제되었다"는 건 다르다.

## 남은 연동 — 검사 이력 (MES · DB)

**파일** `src/services/history.ts`

함수 시그니처를 전부 `Promise`로 잡아 뒀으므로 `localStorage` 호출부만 `fetch`로 바꾸면
호출하는 쪽은 안 바뀐다.

```
loadHistory()                    → GET  /inspections?lot=&from=&to=
saveInspection(item)             → POST /inspections
updateInspection(id, patch)      → PATCH /inspections/:id
```

`buildSeed()`는 가상 데이터 생성기이므로 실제 연결 시 제거한다.

로트/웨이퍼 번호는 지금 사용자가 직접 입력한다. MES에 붙으면 현재 처리 중인 로트를 자동으로
가져오고, 로트의 공정 경로(어느 장비를 지나왔는지)까지 받으면 **원인 추적의 commonality 분석이
자동화된다** — 지금은 "이력 대조 필요"로만 표시하고 사람이 직접 보게 되어 있는 부분이다.

## 판정 규칙을 고칠 때

`npm run verify`가 프리셋 9종의 계통·1순위 클래스를 회귀 기준선과 대조한다. 판정 규칙
(`classify.ts`), 피처(`features.ts`), 계획(`plan.ts`)을 건드렸으면 반드시 돌릴 것.
기준선이 깨지면 **고친 게 맞는지 기준선이 틀렸는지를 먼저 판단하고** 둘 중 하나를 고칠 것.

이 하네스가 실제로 잡아낸 것들:

- 대각 스크래치가 4-연결로 5개 군집으로 쪼개지던 문제 → 8-연결로 교체
- 8×8에서 외곽 링만으로 밀도 임계를 넘어 Edge-Ring이 Near-full로 오분류되던 문제
  → 전면의 서명은 밀도가 아니라 "최내측까지 찼는가"
- **링의 평균 반경은 정의상 중간값**이라 무게중심으로는 Donut을 절대 못 잡던 문제
  → 반경 프로파일의 형상(한 구간이 꽉 참 + 최내측 빔 + 중심을 둘러쌈)으로 판별
- 외곽 링에 붙은 군집이 격자 기하 때문에 저절로 직선이 되어 전부 Scratch로 읽히던 문제

실제 모델이 붙은 지금 이 하네스의 대상은 규칙 대체판(`classify.ts`)이다. 모델 자체의 회귀는
`npm run verify:model`이 맡는다 — 모델 패키지 예시 8종을 실제 서버에 넣어
`python app.py --manual`과 같은 판정이 나오는지 대조한다.
